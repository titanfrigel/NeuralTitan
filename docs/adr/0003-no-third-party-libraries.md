# Third-party libraries in the build

## Context and problem

The project exists so the author can understand every part of an LLM by reviewing code written from first principles. Libraries such as cuBLAS, cuDNN, CUTLASS, Eigen, JSON parsers or test frameworks would either hide exactly the parts the project is meant to expose, or add code nobody on the project has reviewed.

## Decision drivers

- Learning value: matmul, softmax, attention, parsing and tokenization must be visible in project code.
- Reviewability: everything in the build is code the author has reviewed.
- Supply-chain simplicity: no third-party code to audit or update.

## Considered options

| Option | Verdict |
|---|---|
| C++ standard library and CUDA runtime only | Chosen: everything else is written in the project. |
| Allow cuBLAS as an optional benchmark backend | Deferred: may be added later through a new ADR as a speed reference, never as a required path. |
| Use a test framework (e.g. GoogleTest) and a JSON library | Rejected: both are small enough to write ourselves, and depending on them would break the rule for little gain. |

## Decision outcome

Chosen: the build links only the C++ standard library and the CUDA runtime. The project writes its own:
- test harness;
- JSON parser;
- safetensors reader;
- checkpoint format;
- Unicode tables (generated by a script and committed as source);
- kernels.

OpenMP is excluded; CPU parallelism uses `std::thread`.

## Consequences

- More code to write and review, which is the point of the project.
- No dependency updates or advisories to track for the library itself.
- Development-only tooling outside the build (see ADR 0004) is governed separately and never linked.
